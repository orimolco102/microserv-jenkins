# קו ייצור לשני שירותים ב-Jenkins — תיעוד תשתית ופריסה

מסמך זה מתעד את שתי השכבות המרכזיות של הפרויקט: הקמת שרת ה-**AWS EC2** המשמש כסביבת היעד, ומנגנון ה-**Blue-Green Deployment** הרץ עליו בכל פריסה.

# חלק א׳ — הקמת שרת AWS EC2

## הקשר למטלה

מסמך זה הוא חלק מהתשתית עבור מטלת ההגשה **"קו ייצור לשני שירותים ב-Jenkins"**. המטלה דורשת (סעיף 5) שהעלייה לאוויר תתבצע בשיטת **Blue-Green Deployment**, כאשר "הבודק פותח כתובת אחת קבועה" ו"בשום שלב בתהליך האתר אינו יורד מהאוויר".

מימוש דרישה זו מחייב שרת (production) נפרד מהמחשב האישי — סביבה שבה קונטיינרי `api`/`web` יכולים לפעול בעקביות, נגישים מכתובת ציבורית קבועה. לשם כך הוקמה מכונת **AWS EC2** ייעודית, שעליה מותקן Docker בלבד.

**Jenkins עצמו רץ On-Prem**, על מחשב אישי (Windows), ומריץ עליו את קו הייצור המלא — בדיקות, בנייה, ודחיפת תמונות ל-Docker Hub. מכונת ה-EC2 משמשת אך ורק כסביבת **production**: Jenkins מתחבר אליה מרחוק דרך SSH בשלב הפריסה, ומריץ עליה `docker compose` כדי להרים את קונטיינרי `api`/`web` (בשני הצבעים, לצורך ה-Blue-Green) ואת שער ה-nginx. חלוקה זו — Jenkins "המוח" של התהליך, EC2 "השרירים" שמריצים את התוצר הסופי — משמעה שעל מכונת ה-EC2 מותקן Docker בלבד, ואין צורך להתקין עליה Jenkins בשום צורה (לא ישירות ולא כקונטיינר).

## שלב 1 — יצירת EC2 Instance

1. כנס ל-**EC2 Console** ולחץ **Launch Instance**
2. **Name:** תן שם למכונה (למשל `2ms-jenkins-server`)
3. **AMI:** בחר **Ubuntu Server 24.04 LTS**
4. **Instance type:** `t3.medium` (2 vCPU, 4GB RAM — מספיק להרצת Docker ומספר קונטיינרים)
5. **Key pair:**
   - צור key pair חדש
   - שמור את קובץ ה-`.pem` שמורד במקום קבוע ונגיש
   - **קובץ זה מוצג פעם אחת בלבד — איבוד שלו מחייב יצירת key pair חדש**
6. **Storage:** שנה מברירת המחדל (8GB) ל-**20GB** — נדרש שטח נוסף עבור Docker images, `node_modules`, ולוגים
7. **Network settings → Edit:** ודא ש-"Allow SSH traffic" מסומן
8. לחץ **Launch Instance**

## שלב 2 — פתיחת פורטים (Security Group)

1. עבור ל-**EC2 → Security Groups**
2. בחר את קבוצת האבטחה המשויכת למכונה שיצרת
3. לחץ **Edit inbound rules**
4. הוסף כללים (**Add rule**) עבור:

   | Type | Port | Source | מטרה |
   |---|---|---|---|
   | SSH | 22 | 0.0.0.0/0 (או ה-IP הספציפי שממנו Jenkins On-Prem מתחבר) | חיבור מרוחק למכונה |
   | Custom TCP | **8000** | 0.0.0.0/0 | הכתובת היחידה שהבודק פותח — פורט ה-gateway של nginx |

   > אין צורך לפתוח פורט נפרד עבור Jenkins UI, שכן Jenkins אינו רץ על מכונה זו כלל.

5. לחץ **Save rules**

> **הערה חשובה לקראת חלק ב׳ (Blue-Green):** הפורט הקבוע ש"פונה" הבודק אליו (8000) הוא בסופו של דבר הפורט שמאזין לו **nginx** — לא הפורט הפנימי הזמני של כל גרסה (blue/green). יש לוודא שהפורט שנפתח כאן ב-Security Group תואם בדיוק לפורט שה-gateway מחזיק.

## שלב 3 — תיקון הרשאות קובץ המפתח (Windows בלבד)

ב-Windows, קובץ ה-`.pem` מקבל כברירת מחדל הרשאות פתוחות מדי, ו-SSH מסרב להשתמש בו. יש להריץ ב-**PowerShell**:

```powershell
icacls "path\to\your-key.pem" /inheritance:r
icacls "path\to\your-key.pem" /remove "Authenticated Users" "SYSTEM" "Administrators" "Users" "BUILTIN\Users"
icacls "path\to\your-key.pem" /grant:r "$($env:USERNAME):(R)"
```

לאימות שההרשאות תקינות (אמורה להופיע שורה אחת בלבד, עם המשתמש הנוכחי בלבד):

```powershell
icacls "path\to\your-key.pem"
```

> **הערה מהניסיון בפועל:** ודאו שקובץ ה-`.pem`/מפתח ה-SSH נמצא על כונן NTFS רגיל (בדרך כלל `C:`). קבצי מפתח שנשמרו על כוננים חיצוניים, כוננים ממופים, או תיקיות תחת WSL (`/mnt/...`) עלולים "לדחות" שינויי הרשאות באופן שקט — הפקודה `icacls` תדווח על הצלחה, אך ההרשאה בפועל לא תשתנה, ו-SSH ימשיך לסרב להשתמש במפתח. זה בדיוק המקרה שקרה בפועל בפרויקט זה, ופתרונו היה העתקת המפתח לתיקייה תחת `C:\Users\<user>`.

## שלב 4 — התחברות למכונה דרך SSH

מצא את ה-**Public IPv4 address** בעמוד ה-instance ב-EC2 Console, והתחבר:

```bash
ssh -i "path\to\your-key.pem" ubuntu@<PUBLIC-IP>
```

> **הערה מהניסיון בפועל:** אם ההתחברות "נתקעת" (`Connection timed out`) ב-Windows דווקא כשמשתמשים ב-`ssh.exe` המובנה (בעוד כלים אחרים כמו MobaXterm מצליחים להתחבר לאותה כתובת ללא בעיה), כדאי להוסיף את הדגל `-4` (המכריח שימוש ב-IPv4 בלבד). מדובר בבעיה ידועה של רזולוציית IPv6 שגורמת ל-`ssh.exe` "להיתקע" בניסיון תקשורת ב-IPv6 לפני שהוא חוזר ל-IPv4.

## שלב 5 — התקנת Docker

```bash
sudo apt update && sudo apt upgrade -y
```

```bash
curl -fsSL https://get.docker.com -o get-docker.sh
sudo sh get-docker.sh
```

```bash
sudo usermod -aG docker $USER
```

**לאחר הפקודה האחרונה יש להתנתק ולהתחבר מחדש** (`exit`, ולאחר מכן שוב פקודת ה-SSH), כדי שהרשאת הקבוצה תיכנס לתוקף.

### יצירת משתמש ייעודי לפריסה

מכיוון ש-Jenkins (הרץ On-Prem) מתחבר למכונה זו אוטומטית בכל פריסה, נוצר משתמש נפרד ומבודד לצורך זה, כדי להפריד בין פעולות אוטומטיות לבין ניהול ידני:

```bash
sudo adduser deploy
sudo usermod -aG docker deploy
```

לאחר מכן הוגדר עבור המשתמש `deploy` זוג מפתחות SSH ייעודי (המפתח הציבורי נוסף ל-`~/.ssh/authorized_keys` שלו), והמפתח הפרטי נשמר כ-Credential בתוך Jenkins (ראו חלק ב׳). כך Jenkins מתחבר תמיד כ-`deploy`, ולא כמשתמש הניהולי `ubuntu`.

### אימות ההתקנה

לאחר ההתחברות מחדש:

```bash
docker --version
docker run hello-world
```

הרצה מוצלחת של `hello-world` (הודעת "Hello from Docker!") מאשרת ש-Docker מותקן ופועל כראוי, כולל הרשאות המשתמש.

### הוספת Swap

במופע `t3.medium` (4GB RAM), הרצת שני סטים מלאים של קונטיינרים בו-זמנית — כפי שקורה בכל מעבר Blue-Green — יוצרת עומס זיכרון רגעי משמעותי. בפועל, ללא swap, זה גרם ל-OOM Killer לחסל תהליכים (`exit code 137`) באמצע בדיקות בריאות. הוספת swap פתרה את הבעיה:

```bash
sudo fallocate -l 2G /swapfile
sudo chmod 600 /swapfile
sudo mkswap /swapfile
sudo swapon /swapfile
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab
```

# חלק ב׳ — מנגנון Blue-Green Deployment

## סקירה כללית

הפרויקט מריץ שני שירותים (`web` ו-`api`) בשני "צבעים" מקבילים — **blue** ו-**green**.
בכל רגע נתון רק צבע אחד "חי" ומקבל תעבורה אמיתית, בעוד השרת השני עומד מוכן לקראת הפריסה הבאה.

המטרה: לאפשר עדכון גרסה חדשה **בלי זמן השבתה (downtime)** — האתר ממשיך לענות למשתמשים לאורך כל תהליך הפריסה, כולל ברגע המעבר עצמו.

## ארכיטקטורה

```
                    ┌─────────────────────┐
   משתמש  ──────▶  │   nginx (gateway)    │  ── פורט 8000 (ציבורי, יחיד)
                    └─────────┬───────────┘
                              │
                 מפנה לפי active.conf
                              │
              ┌───────────────┴───────────────┐
              ▼                                ▼
      ┌───────────────┐               ┌───────────────┐
      │  web-blue      │               │  web-green     │
      │  api-blue      │               │  api-green     │
      └───────────────┘               └───────────────┘
         (חי כרגע)                       (הצבע החדש בפריסה)
```

- **nginx** הוא המכולה היחידה החשופה כלפי חוץ, בפורט 8000 — הפורט שנפתח ב-Security Group בחלק א׳.
- הקובץ `nginx/conf.d/active.conf` קובע לאיזה צבע (`blue` או `green`) nginx מפנה כרגע — הן בפורט הציבורי (8000) והן בפורט הפנימי (3001) שדרכו `web` פונה ל-`api`.
- שני קבצי תבנית קבועים — `active.blue.conf` ו-`active.green.conf` — מכילים כל אחד את ההגדרה המלאה עבור הצבע המתאים. המעבר בין צבעים הוא פשוט **החלפת קובץ** ו-reload ל-nginx.

## חיבור Jenkins (On-Prem) לשרת ה-EC2

בכל פריסה, Jenkins שרץ מקומית מבצע את הפעולות הבאות מול ה-EC2:

1. **אריזה** — הקבצים `docker-compose.prod.yml`, `deploy.sh`, ותיקיית `nginx/` נארזים לקובץ ארכיון יחיד (`tar`) ב-Jenkins עצמו, לפני ההעברה.
2. **העברה** — הארכיון מועבר בפעולת `scp` **בודדת** אל המכונה.
3. **הרצה מרחוק** — חיבור `ssh` **יחיד** מחלץ את הארכיון, מתקן קידומי שורה (CRLF→LF, שכן הקובץ נבנה על Windows), ומריץ את `deploy.sh`.

צמצום מספר החיבורים לשניים בלבד (במקום חיבור נפרד לכל קובץ) נעשה בעקבות בעיה שהתגלתה בפועל: פתיחת מספר חיבורי SSH/SCP רצופים בזמן קצר גרמה לחסימה זמנית של החיבורים (ככל הנראה הגנת flood ברמת הרשת הביתית), שהתבטאה בשגיאות `Connection timed out` חוזרות. איחוד כל ההעברה לחיבור אחד פתר את הבעיה לחלוטין.

האימות מתבצע באמצעות Credential מסוג **SSH Username with private key** בתוך Jenkins, עבור משתמש ה-`deploy` שהוגדר בחלק א׳.

## תהליך הפריסה (מבוצע על ידי `deploy.sh`)

1. **זיהוי הצבע החי** — הסקריפט קורא את `active.conf` ומזהה איזה צבע פעיל כרגע. יש גם בדיקת שפיות: אם `active.conf` מצביע על צבע שלמעשה לא רץ (מצב שקרה בפועל בעקבות פריסות שנכשלו באמצע), הסקריפט מזהה זאת מול `docker ps` בפועל, ומתקן את עצמו אוטומטית במקום להיכנס למצב שגוי שגורם ל-nginx לקרוס.
2. **הרמת הצבע החדש** — המכולות של הצבע השני (`web` ו-`api`) עולות **לצד** הצבע החי, מבלי לגעת בו, תוך שימוש ב-`--force-recreate` כדי להבטיח שהמכולה אכן נוצרת מחדש מהתמונה שנמשכה. הפריסה מציינת תגית תמונה מפורשת (תואמת למספר ה-build של Jenkins, לדוגמה `:47`) במקום `latest` — בפועל התגלה שהסתמכות בלעדית על `latest` גרמה לכך שקונטיינרים המשיכו להריץ תמונה ישנה בת שעות רבות, מבלי ש-`docker compose pull` באמת משך את הגרסה העדכנית.
3. **בדיקת בריאות (health check)** — הסקריפט שולח בקשות אל `/health` (ל-`api`) ואל `/status` (ל-`web`) של הצבע החדש, עד 10 ניסיונות בהפרשי 3 שניות, עם timeout של 10 שניות לכל בקשה (כדי לתת מרווח ל"עלייה קרה" של קונטיינר Node חדש). הבדיקה מתבצעת **דרך מכולת ה-nginx**, שכן היא משותפת לרשת הפנימית ויכולה לפנות לשני הצבעים ישירות בשמם.
4. **הצלחה → מעבר** — אם הבדיקה עברה, הקובץ `active.conf` מוחלף בגרסה של הצבע החדש, ו-nginx מקבל פקודת `reload`. פקודת ה-reload **אינה סוגרת את הסוקט המאזין** — כלומר אף בקשה לא נדחית ברגע המעבר עצמו. לאחר מכן המכולות של הצבע הישן נסגרות (בהתייחסות ישירה לשמן, ולא באמצעות `--profile`, כדי לא לפגוע בטעות במכולת ה-nginx המשותפת).
5. **כישלון → החזרה אחורה (rollback)** — אם הבדיקה נכשלת בכל 10 הניסיונות, מכולות הצבע החדש מוסרות, `active.conf` נשאר ללא שינוי, והצבע הישן ממשיך לשרת תעבורה כרגיל. הפריסה נכשלת בבירור (exit code שונה מ-0), כך ש-Jenkins מדווח על כישלון.

## איך מתבצע המעבר בפועל

כפי שנדרש, מנגנון המעבר מבוסס על **מכולת nginx קטנה** שמשמשת כשער כניסה יחיד. בסיום תהליך הבדיקה, ההגדרה הפנימית שלה מוחלפת כך שתפנה למכולה החדשה במקום לישנה, ולאחר מכן מתבצע reload. גישה זו נבחרה (על פני החלפת הפורט החיצוני עצמו) כיוון שהיא:

- מאפשרת בדיקת בריאות מלאה על הצבע החדש **לפני** שהוא נחשף למשתמשים כלל.
- לא דורשת שינוי כלשהו בצד הלקוח או בכתובת החיצונית (הבודק ממשיך לפתוח את אותה כתובת קבועה, פורט 8000).
- מבטיחה שקוד ה-`web` לא צריך לדעת איזה צבע פעיל — הוא תמיד פונה ל-`api` דרך הפורט הפנימי של nginx (3001), ו-nginx הוא זה שמנתב בפועל.

## הרצה ידנית (לצורך בדיקה/דיבוג)

```bash
# הרמת צבע מסוים ידנית
docker compose -f docker-compose.prod.yml --profile blue up -d

# הרצת תהליך הפריסה המלא
./deploy.sh

# בדיקת מצב נוכחי
curl http://localhost:8000/status
docker ps
```
